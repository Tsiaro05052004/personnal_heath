1. PRINCIPES DIRECTEURS
--------------------------------------------------------------------------------
Les exigences du cahier des charges qui guident les choix :

  - Hors ligne d'abord : le suivi doit fonctionner sans Internet une fois
    configuré  →  base de données LOCALE = source de vérité, le serveur sert
    à l'authentification et à la sauvegarde/synchronisation.
  - Notifications même application fermée  →  notifications PLANIFIÉES par
    le système Android (pas un minuteur dans l'application).
  - Données médicales confidentielles  →  chaque ligne appartient à un
    utilisateur, protégée côté serveur (Row Level Security) ; session stockée
    dans un stockage chiffré.
  - Utilisateurs âgés / non techniciens  →  interface simple, grands boutons,
    navigation par barre en bas avec 5 onglets maximum.
  - Règle médicale : l'application rappelle et compte, elle ne conseille
    jamais (pas de calcul de dose, pas de « doublez la prise »).

Organisation : « feature-first ». Chaque fonctionnalité du cahier des charges
a son propre dossier, découpé selon la CLEAN ARCHITECTURE en 3 couches
(domain / data / presentation) + un petit dossier d'injection (di/).
La couche presentation suit le patron MVVM (View / ViewModel / UiState).
Le code partagé par plusieurs fonctionnalités va dans core/.


2. CHOIX TECHNIQUES
--------------------------------------------------------------------------------
  Besoin                     Paquet / service           Pourquoi
  -------------------------  -------------------------  ---------------------------
  Gestion d'état             flutter_riverpod           Simple, testable, pas de
                                                        BuildContext nécessaire
  Navigation                 go_router                  Routes nommées, redirection
                                                        si non connecté, onglets
  Base locale (hors ligne)   drift (SQLite)             Requêtes typées, flux
                                                        réactifs (Stream), migrations
  Backend : auth + données   supabase_flutter           PostgreSQL + RLS (chaque
                                                        utilisateur ne voit que ses
                                                        données), proposé par le CDC
  Stockage sécurisé          flutter_secure_storage     Jetons de session chiffrés
  Notifications planifiées   flutter_local_notifications  Fonctionnent appli fermée,
                             + timezone                 planification à l'heure exacte
  Tâches en arrière-plan     workmanager                Replanifier les rappels
                                                        chaque jour, synchroniser
  Carte                      flutter_map + latlong2     OpenStreetMap (exigé par
                                                        le CDC)
  Hôpitaux à proximité       API Overpass (OSM)         Données OSM : amenity=hospital,
                             via package http           clinic, doctors, healthcare=*
  Géolocalisation            geolocator                 Position + calcul de distance
  Permissions                permission_handler         Localisation, notifications,
                                                        alarmes exactes
  Itinéraire / appel         url_launcher               Ouvre l'appli GPS ou le
                                                        téléphone
  Dates / format FR          intl                       Heures et dates en français

  REMARQUE : le CDC laisse le choix Supabase / Firebase. Supabase est recommandé
  ici (SQL relationnel adapté aux médicaments/horaires/prises, RLS simple).
  Grâce au découpage en couches, seul le dossier data/remote changerait si on
  passait à Firebase.

4. CLEAN ARCHITECTURE : RÔLE DES COUCHES ET RÈGLES DE DÉPENDANCE
--------------------------------------------------------------------------------
  domain        →  Le cœur : entités, interfaces de dépôts, use cases et
                   règles du cahier des charges. Dart pur. C'est ici qu'on
                   teste « 2 comprimés = 1 prise » ou « non confirmée ≠
                   oubliée ». Un use case peut combiner plusieurs interfaces
                   (ex. ConfirmIntake : enregistrer la prise ET annuler les
                   rappels de suivi).

  data          →  Implémente les interfaces du domaine. Lit et écrit les
                   données, écrit TOUJOURS d'abord en local (hors ligne) puis
                   marque la ligne « à synchroniser ». Convertit les lignes
                   Drift / JSON en entités via ses mappers.

  presentation  →  Affiche l'état et transmet les actions de l'utilisateur
                   (MVVM, section 5). Ne contient AUCUNE règle métier ni
                   appel SQL/réseau ; ne parle qu'aux use cases.

  di            →  Branche data sur domain avec des providers Riverpod
                   (inversion de dépendance). La présentation lit les use
                   cases ici, sans jamais importer data/ elle-même.

  Sens des dépendances :

        presentation ──→ domain ←── data
              │                       ▲
              └──→ di ────────────────┘   (di connaît les deux pour câbler)

  Règles (vérifiées automatiquement par test/architecture/
  dependency_rules_test.dart) :
  - domain/ n'importe que dart:* (sauf dart:ui) et d'autres fichiers domain/.
  - data/ n'importe ni presentation/, ni Flutter, ni app/.
  - presentation/ n'importe ni data/, ni core/database/, ni Drift, ni
    Supabase, ni app/.
  - core/ n'importe ni app/, ni data/, ni presentation/, ni di/ d'une
    feature. Exception assumée : core/database/ (infrastructure de data)
    importe les énumérations de domain/entities/ pour les stocker
    (textEnum).
  - app/ assemble tout : rien ne dépend de app/.
  - Entre features : on n'importe que le domain/, le di/ ou les libellés
    (presentation/mappers/) d'une autre feature, jamais sa data/, ses
    écrans ni ses ViewModels (ex. dashboard utilise dayPlanProvider,
    ConfirmIntake et DoseLabels de medications).


5. MVVM : LA COUCHE PRÉSENTATION
--------------------------------------------------------------------------------
  View (screens/, widgets/)
    - ConsumerWidget. Affiche ref.watch(xxxViewModelProvider) et appelle
      ref.read(xxxViewModelProvider.notifier).onAction(...).
    - Aucune logique : pas de calcul, pas d'accès aux use cases ni aux
      dépôts. Gère seulement ce qui exige un BuildContext (navigation,
      SnackBar, dialogues) en réaction à l'état.

  ViewModel (viewmodels/<ecran>_view_model.dart)
    - Notifier<UiState> ou AsyncNotifier<UiState> de Riverpod, un par écran
      (ou par fiche/formulaire complexe).
    - Reçoit les use cases via ref.watch(...) sur les providers de di/.
    - Transforme les entités en UiState prêt à afficher ; expose des
      méthodes d'action (confirmIntake, addGlass, save…).
    - N'importe JAMAIS package:flutter/material.dart, ne manipule ni
      BuildContext ni widget → testable avec un simple ProviderContainer.

  UiState (viewmodels/<ecran>_ui_state.dart)
    - Classe immuable (champs final + copyWith) : tout ce que l'écran
      affiche, y compris chargement / erreur / message de réussite.
    - AsyncValue<UiState> pour les états chargement/erreur des données
      asynchrones.

  Flux à sens unique :
      View ──action──→ ViewModel ──→ UseCase ──→ Repository (interface)
       ▲                   │
       └──── UiState ──────┘   (les Stream Drift remontent jusqu'au
                                ViewModel, qui publie un nouvel état)

  Les écrans provisoires actuels (étape 1) n'ont ni état ni action : ils
  n'ont donc pas encore de ViewModel. Chaque écran en reçoit un dès qu'il
  affiche des données (à partir de l'étape 2).


6. RÔLE DE CHAQUE FONCTIONNALITÉ

6.1 auth/  (Connexion / Inscription)

  - Connexion, déconnexion, mot de passe oublié.

  - authStateProvider (di/) : écouté par router.dart pour rediriger.
  Écrans : login_screen, register_screen.

6.2 dashboard/  (Accueil)  — FAIT (étape 5)
  - Ne stocke rien : il AGRÈGE dayPlanProvider (medications/di) et
    waterDayProvider (hydration/di).
  - domain/services/daily_summary_calculator.dart → DailySummary :
    prises regroupées par heure (IntakeGroup, « 20h00 · Paracétamol,
    Amoxicilline »), état d'un groupe (en attente > non confirmée > à venir
    > non pris > pris ; « pris » seulement si toutes le sont), prochaine
    prise (IntakePlanner.nextIntake), eau du jour. Réutilisé par history/.
  - Écran (maquette 2) : date + « Bonjour » (prénom à l'étape 7), bouton
    profil → Paramètres, carte « Prochaine prise » (en attente depuis /
    dans …, « Confirmer la prise » dès 30 min avant), sinon « Aucun
    médicament » (→ ajout) ou « Plus de prise prévue aujourd'hui » (avec
    le nombre de prises non confirmées → onglet Médicaments) ; compteurs
    Médicaments / Eau (→ onglets) ; liste « Aujourd'hui » + « Tout voir ».
  ViewModel : DashboardViewModel (confirmation via ConfirmIntake).

6.3 medications/  (Mes médicaments + Suivi des prises)  — FAIT (étape 2)
  Entités (domain/entities) :
  - Medication : id, nom, dosage (« 500 mg »), quantitéParPrise (ex. 2
    comprimés), unité, consigne repas, remarques, dateDébut, dateFin
    (incluse, null = sans fin), doseTimes (heures de prise). La FRÉQUENCE
    n'est pas stockée : c'est le nombre d'horaires.
  - DoseTime : heure de prise (stockée en minutes depuis minuit).
  - IntakeLog : prise sur laquelle l'utilisateur a agi : statut (pris |
    non pris), heure prévue, heure RÉELLE, quantité prise.
  - ScheduledIntake + IntakeState : prise prévue un jour donné et son état
    affiché (calculé, jamais stocké). DayPlan : toutes les prises d'un jour,
    regroupées par médicament (MedicationDay).
  Règles (domain/services) :
  - intake_planner.dart — état d'une prise :
      Pris           → IntakeLog « pris » (heure réelle affichée)
      Non pris       → l'utilisateur l'a déclaré lui-même
      En attente     → heure passée depuis moins de 2 h, pas de log
      Non confirmée  → heure passée depuis plus de 2 h, pas de log
                       (JAMAIS « oubliée » automatiquement)
      À venir        → plus tard
    Confirmation possible dès 30 min avant l'heure, et en retard (l'heure
    réelle est enregistrée), même après « non pris ». « Je ne l'ai pas
    pris » seulement une fois l'heure passée. Prochaine prise = la plus
    ancienne en attente, sinon la prochaine à venir (pour l'Accueil).
    Compteur « 1 prise sur 3 » = prises confirmées / prises prévues ;
    unités consommées = somme des quantités (distinct des prises).
    Avant dateDébut / après dateFin : aucune prise prévue → aucun rappel.
  - medication_rules.dart — saisie : nom obligatoire, au moins un horaire,
    pas deux fois la même heure, quantité > 0, fin ≥ début ; horaires
    proposés selon 1× à 4× par jour (08:00 / 14:00 / 20:00…). L'appli
    recopie l'ordonnance, elle ne propose ni ne modifie jamais de dose.
  Use cases : WatchMedications, GetMedication, SaveMedication,
  DeleteMedication (suppression logique ; l'historique des prises reste),
  WatchDayPlan, ConfirmIntake, MarkIntakeMissed.
  SaveMedication / DeleteMedication replanifient les rappels ;
  ConfirmIntake / MarkIntakeMissed annulent ceux de la prise ;
  RescheduleReminders, SnoozeReminder (voir section 7).
  di/ : medicationRepositoryProvider + un provider par use case +
  dayPlanProvider(jour) (réutilisé par l'Accueil).
  ViewModels : MedicationListViewModel (jour choisi, plan du jour,
  confirmer / non pris), MedicationFormViewModel (formulaire en 3 étapes,
  family par id).
  Écrans (maquettes 3 et 4) :
  - medication_list_screen : bandeau de 5 jours, une carte par
    médicament avec ses prises, bouton « Confirmer » sur les prises en
    attente, fiche du bas au toucher d'une prise (« J'ai pris mon
    médicament » / « Je ne l'ai pas pris » + rappel « ne doublez jamais
    une dose »), « Ajouter un médicament ».
  - medication_form_screen (/medicament/nouveau, /medicament/:id) :
    1. Médicament (nom, dosage, forme) ; 2. Horaires (1× à 4×, heures,
    quantité par pas de 0,5) ; 3. Durée et consignes (repas, début, fin,
    remarques). Suppression depuis l'icône corbeille en modification.
  - intake_alarm_screen (/alarme?med=…&at=…, maquette 7) : voir section 7.

6.4 hydration/  (Hydratation)  — FAIT (étape 4)
  Entités : WaterSettings (objectifVerres, mlParVerre, réveil, coucher en
  minutes depuis minuit, rappelsActivés), WaterLog (un verre bu, avec SA
  quantité), WaterDay (verres, ml, objectif atteint, progression plafonnée),
  WaterReminder (nudge | summary).
  Règles (domain/services) :
  - water_reminder_planner.dart : au plus 8 rappels par jour, répartis
    régulièrement entre réveil et coucher (arrondis au quart d'heure),
    chacun avec un objectif intermédiaire (5 verres, 7h–22h : 9h30→1,
    12h→2, 14h30→3, 17h→4, 19h30→5). Un rappel dont l'objectif
    intermédiaire est atteint n'est pas planifié → replanification à
    chaque verre. Bilan 30 min avant le coucher (atteint ou non, sans
    reproche). Fenêtre de 7 jours.
  - water_rules.dart : 1 à 20 verres, verres de 50 à 1000 ml, coucher au
    moins 2 h après le réveil (pas de passage de minuit).
  - Jamais « buvez N verres maintenant » ; aucune quantité recommandée
    (« demandez conseil à votre médecin »).
  Use cases : WatchWaterDay, GetWaterSettings, SaveWaterSettings, AddGlass,
  UndoLastGlass (suppression logique), RescheduleWaterReminders.
  Rappels : WaterReminderGateway (domaine) → NotificationWaterReminderGateway
  (data) : canal « rappels_eau », simple notification (pas de sonnerie de
  réveil ni de plein écran), payload {"type":"eau"} ; toucher → onglet Eau.
  di/ : waterDayProvider(jour) réutilisé par l'Accueil et l'Historique.
  Écrans (maquette 5) : hydration_screen (anneau, ml, verres, « J'ai bu un
  verre », « Annuler le dernier verre », encart prochain rappel ou
  félicitations ; carte « Définissez votre objectif » au premier
  lancement), water_goal_screen (/eau/objectif).

6.5 hospitals/  (Carte)
  - location_service : position de l'utilisateur (avec autorisation).
  - remote/overpass_api.dart : récupère hôpitaux, cliniques et centres de
    santé dans un rayon donné (requête Overpass sur les données OSM).
  - local : met en cache le dernier résultat (carte utilisable hors ligne
    avec les derniers établissements connus).
  - Entité HealthFacility : nom, type, adresse, lat/lng, téléphone (si

  - Recherche par nom ou par lieu (filtre local + requête Overpass).
  - Itinéraire / appel : url_launcher (ouvre Google Maps / OsmAnd / le
    composeur téléphonique).
  - Tuiles OSM : renseigner userAgentPackageName et l'attribution
    « © OpenStreetMap contributors » ; pour une publication, prévoir un

  - Afficher un avertissement : les informations peuvent être obsolètes.
  Écrans : hospitals_map_screen, facility_detail_sheet (fiche en bas).

6.6 history/  (Historique)
  - Liste des jours passés avec leur bilan (réutilise

6.7 settings/  (Paramètres)

7. SYSTÈME DE RAPPELS (point le plus sensible)  — FAIT pour les médicaments
--------------------------------------------------------------------------------
  Qui fait quoi :
    domain/services/reminder_planner.dart   règles pures (testées)
    domain/repositories/reminder_gateway.dart  interface : replaceAll,
                                            snooze, cancelFor, autorisations
    domain/usecases/reschedule_reminders.dart  médicaments + prises → plan
                                            → gateway
    data/reminders/notification_reminder_gateway.dart  implémentation avec
                                            core/notifications
    presentation/mappers/reminder_texts.dart  texte des notifications
                                            (injecté par di/)

  Fonctionnement :
  1. ReminderPlanner calcule les rappels sur une fenêtre glissante de
     14 jours, les plus proches d'abord, plafonnés à 300 (Android limite
     une appli à ~500 alarmes ; marge gardée pour l'eau).
  2. Pour chaque prise prévue non encore confirmée ni déclarée non prise :
       - rappel à l'heure prévue ;
       - 2e rappel 30 min après (ReminderPlanner.followUpDelay).
     Avant la date de début / après la date de fin : aucun rappel.
  3. Les notifications sont planifiées par Android (sonnent appli fermée,
     replanifiées par le plugin après un redémarrage). Mode « réveil »
     (setAlarmClock) si l'autorisation des alarmes exactes est accordée :
     c'est le seul mode que ColorOS (Realme/Oppo) ne retarde pas — en mode
     « exact » simple, le Realme de test décalait les rappels jusqu'à 1 h.
     Effet visible : icône de réveil dans la barre d'état. Sans
     l'autorisation, mode inexact (Android peut décaler).
     Notification plein écran (catégorie alarme) avec le bouton « J'ai
     pris mon médicament ».
  4. La passerelle compare avec les notifications en attente : elle ne
     replanifie que les nouvelles ou modifiées (empreinte du texte et de
     l'heure dans le payload) et annule celles qui ne sont plus voulues.
     Les rappels « plus tard » sont conservés, ainsi que ceux déjà dus mais
     pas encore affichés (sinon rouvrir l'appli pile à l'heure les
     annulait). Changer la façon de planifier → incrémenter
     NotificationReminderGateway.scheduleVersion pour tout replanifier.
  5. Replanification : au démarrage, au retour dans l'appli, après
     ajout / modification / suppression d'un traitement et après
     l'autorisation des notifications.
  6. Confirmer ou déclarer non prise → annule tous les rappels de cette
     prise (y compris la notification affichée).
  7. Alarme sonore (option, ACTIVÉE par défaut, alarmSoundEnabledProvider ;
     interrupteur dans Paramètres à l'étape 8) : canal Android séparé
     « alarme_medicaments » — sonnerie de réveil du téléphone, volume du
     réveil (USAGE_ALARM), répétée (FLAG_INSISTENT), coupée au bout de
     5 min si personne ne réagit (le 2e rappel sonne 30 min après). Sans
     l'option : canal « rappels_medicaments », son de notification.
     La sonnerie continue pendant l'affichage de l'écran d'alarme (Android
     l'ouvre de lui-même) ; elle s'arrête sur une réponse ou en quittant
     l'écran (SilenceReminder : seulement les rappels déjà affichés).
  8. Toucher la notification → écran d'alarme (route /alarme, maquette 7) :
     « J'ai pris mon médicament », « Me le rappeler dans 10 min »,
     « Je ne l'ai pas pris », rappel « ne doublez jamais une dose ».
     Le bouton « J'ai pris » de la notification ouvre l'appli et confirme
     directement (traité dans l'appli : base locale, pas d'isolate de fond).
  9. Autorisations : demandées après l'enregistrement d'un médicament,
     avec une explication d'abord (jamais au premier lancement).

  Reste à faire :
  - Rafraîchissement quotidien en arrière-plan (workmanager) : sans lui,
    si l'appli n'est jamais rouverte pendant 14 jours, les rappels
    s'arrêtent. Chaque toucher de rappel rouvre l'appli et prolonge la
    fenêtre, ce qui couvre l'usage normal.
  - Interrupteur « Alarme sonore » et délai du 2e rappel (étape 8,
    Paramètres) ; rappels d'eau (étape 4) dans le canal « rappels_eau ».

  Configuration Android requise (AndroidManifest.xml) :
  - POST_NOTIFICATIONS (Android 13+)
  - SCHEDULE_EXACT_ALARM (heure exacte ; demandée à l'utilisateur sur
    Android 14+. USE_EXACT_ALARM écarté : réservé aux réveils/agendas sur
    le Play Store)
  - RECEIVE_BOOT_COMPLETED (replanifier après redémarrage)
  - USE_FULL_SCREEN_INTENT + showWhenLocked/turnScreenOn sur l'activité
    (écran d'alarme téléphone verrouillé)
  - Récepteurs du plugin : ScheduledNotificationReceiver,
    ScheduledNotificationBootReceiver, ActionBroadcastReceiver
  - Gradle : désucrage Java (desugar_jdk_libs), compileSdk ≥ 36
    (flutter_local_notifications 22 ; la 23 exige compileSdk 37)
  - ACCESS_FINE_LOCATION / ACCESS_COARSE_LOCATION (carte)
  - INTERNET
  Note : certaines marques (dont Realme/Oppo, le téléphone de test)
  bloquent les applications en arrière-plan. Il faut guider l'utilisateur
  pour désactiver l'optimisation de batterie de l'application.


8. DONNÉES ET SYNCHRONISATION
--------------------------------------------------------------------------------
  Tables (identiques en local Drift et sur Supabase) :
    profiles, medications, medication_schedules, intake_logs,
    water_settings, water_logs
  (+ hospitals_cache : uniquement en local)

  Les classes de lignes Drift sont suffixées « Row » (MedicationRow,
  IntakeLogRow…) pour ne pas se confondre avec les entités du domaine.

  Chaque ligne a : id (UUID généré sur le téléphone), user_id,
  updated_at, deleted (suppression logique) et, en local, un indicateur
  « à synchroniser ».

  Supabase : Row Level Security activée sur toutes les tables avec la
  règle « user_id = auth.uid() » → un utilisateur ne peut jamais lire
  les données d'un autre.

  Synchronisation : à l'ouverture, au retour du réseau et périodiquement :
  envoi des lignes « à synchroniser », puis récupération des lignes
  modifiées depuis la dernière synchro (la plus récente gagne).


9. FLUX D'EXEMPLE : « Confirmer la prise »
--------------------------------------------------------------------------------
  IntakeTrackingScreen (bouton)                       [View]
     → IntakeTrackingViewModel.confirmIntake(prise)    [ViewModel]
     → ConfirmIntake(prise, maintenant)                [domain : use case]
         ├─ crée l'entité IntakeLog (statut pris, heure RÉELLE)
         ├─ MedicationRepository.recordIntake(log)     [domain : interface]
         │    → MedicationRepositoryImpl               [data]
         │        └─ mapper → écrit dans Drift (dirty = true → à synchroniser)
         └─ ReminderPlanner.cancelFollowUps(prise)     [domain : interface]
              → implémentation dans core/notifications
     → Drift émet un Stream → WatchTodayIntakes → le ViewModel publie un
       nouvel UiState → l'écran se redessine
     → le compteur « 2 prises sur 3 » et le tableau de bord se rafraîchissent
